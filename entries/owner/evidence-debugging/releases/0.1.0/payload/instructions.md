# 证据驱动调试与验证门禁

## 目标
把失败现象拆成证据链，区分确认、观察、推断和待验证项，完成最小修复并逐层验证。

## 输入
- 证据、相关源码或配置、当前失败现象

## 输出
- 定位结论、最小改动、回归结果、未验证项

## 适用场景
- 跨模块 bug 定位
- 运行时问题追踪
- 发布前检查

## 不适用场景
- 无运行证据直接下结论
- 未经授权扩大修改范围

## 执行步骤

1. 先确认任务目标、环境、当前基线和已授权的副作用。
2. 收集与问题直接相关的原始材料，建立“已确认、观察、推断、待验证”四类证据。
3. 按输入到输出的链路逐步执行；每一步记录使用的工具、文件衔接、产物和失败条件。
4. 先做最小范围变更或本地草稿，再执行与风险相称的静态、回归、运行时或安装检查。
5. 报告已验证结果、未验证项、阻断原因和下一步，不把命令成功等同于业务通过。

## 依赖、权限与副作用

- 工具：Codex、filesystem.read、filesystem.write
- 能力：filesystem.read、filesystem.write、process.execute
- 副作用：read_only、local_generate、project_write
- 远程写入、发布、外部发送、后台导入和生产变更必须由当前任务单独授权。

## 示例

以一个团队内部任务为例：先给出目标和失败证据，再按上述链路生成中间记录，最后附上产物位置和验证结果。示例是方法示范，不把未执行的业务结果写成已通过。

## 来源与限制

本条目由本机 Codex 会话中反复使用的工作方法整理而来；没有复制原始聊天。具体项目路径和版本需要按当前任务重新核对，历史会话只作为方法来源。
