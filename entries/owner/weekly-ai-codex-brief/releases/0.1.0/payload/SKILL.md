# AI 与 Codex 每周简报

## 工作流程

1. 以用户当前时区和日期为准，默认检索最近 7 天，并在简报开头写明日期范围。
2. 回看当前任务中上一期简报，建立已报道主题清单。除非出现实质进展，否则不重复。
3. 先查 OpenAI 官方来源：Codex changelog、ChatGPT release notes、OpenAI 官方博客和官方文档。
4. 再查社区来源：`openai/codex` GitHub Issues、Discussions、Reddit、技术博客和公开实践案例。
5. 打开原始页面核对发布日期、版本、功能状态和适用范围。不要把搜索摘要或抓取日期当作发布日期。
6. 从全部候选中只保留 5 至 8 条最有价值的信息。
7. 用中文生成可直接阅读和分享的 Markdown 简报。

## 选择标准

按以下优先级筛选：

1. Codex 新功能、重要修复或工作流变化。
2. Skills、Plugins、`AGENTS.md`、多代理、自动化和模型选择。
3. 能直接复用的真实案例或技巧。
4. 可能影响稳定性、成本、权限、数据安全或工作质量的风险。
5. 对非技术岗位扩展能力有实际启发的 AI 研究或案例。

没有重大更新时，不要用低价值新闻凑数。改为整理本周新增的高质量案例、可复用技巧或值得观察的问题。

## 证据分层

将内容严格分为以下三类：

- **官方确认**：功能、模型、版本、规则和发布日期必须由 OpenAI 官方资料支持。
- **社区经验**：标明这是个人实践或讨论，不把热度、点赞或单个案例当成真实性证明。
- **争议或风险**：区分已确认缺陷与用户报告。开放 Issue 只能表述为“有人报告”或“仍待确认”。

涉及 OpenAI 产品能力时，以官方资料为最终依据。社区文章若与官方资料冲突，明确指出差异，不替社区说法补强结论。

## 单条格式

每条信息必须包含：

- **发布日期**
- **核心内容**
- **为什么值得关注**
- **直接可用的技巧**
- **来源链接**

来源链接直接指向原始页面，不链接搜索结果页。少量相关来源可并列，但不要堆砌链接。

## 输出结构

使用以下顺序：

1. 标题与时间范围。
2. 一句话结论，指出本周最重要的变化。
3. `官方确认`。
4. `社区经验`。
5. `争议或风险`。
6. `本周建议动作`，给出 3 至 5 个可以立即执行的动作。

保持简洁，不写泛泛的行业新闻摘要。所有判断都应帮助用户决定“本周需要知道什么、试什么、避免什么”。

## 去重规则

- 旧功能只有新增版本、正式发布、明显能力变化或风险状态改变时才再次收录。
- 再次收录时明确写出“与上期相比新增了什么”。
- 同一版本的多个小修复可以合并为一条，不拆分凑数量。
- 同一社区观点被多人转述，不视为多个独立证据。
